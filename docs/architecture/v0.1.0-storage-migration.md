# v0.1.0 storage migration and rollback contract

The v0.1.0 migration is an in-place application upgrade. It keeps the bundle identifier and
workspace format unchanged, preserves every v0.0.5-owned value, and creates only versioned v0.1.0
state. A migration failure selects the legacy runtime for that process; it never repairs a damaged
record by guessing or deleting user data.

## Persisted-state inventory

Physical app-config and app-data paths are resolved by Tauri for the current operating system and
application identifier. The table uses logical paths so code and tests do not depend on a user's
home directory.

| Store | Logical key or path | Owner and contents | v0.1.0 disposition |
| --- | --- | --- | --- |
| Workspace | User-selected directory | Markdown, media and project files | Never migrated or rewritten by startup migration. Document writes still require the normal optimistic revision and atomic-write path. |
| App config | `runtime-mode.json` | Schema 1 `legacy`/`v2` selection | Validate if present and retain byte-for-byte. Invalid JSON/schema fails safe to legacy. |
| App config | `workspace-startup.json` | Schema 1 default workspace path and startup preference | Validate if present and retain byte-for-byte. No path is copied into the migration ledger. |
| App data | `migration-v0.1.0.json` | Schema 1 completion ledger containing category names, dispositions and presence booleans | New private, atomically replaced file. Written last after app-data validation. It contains no workspace path or document content. |
| App data | `document-recovery-v1/<workspace-hash>/` | V2 current/previous recovery generations, checksums and dirty buffers | New V2-only namespace. It is not read by v0.0.5 and is subject to the recovery store's permissions, checksum and quota gates. |
| App data | Window state | No persisted v0.0.5 window-state file was found | Recorded as absent; no synthetic state is created. |
| WebView localStorage | `<app>:default-template`, `read-mode`, `outline-collapsed`, `kanban-open`, `ticket-layout`, `kanban-filter`, `kanban-filter-presets` | v0.0.5 UI/plugin preferences | Retained unchanged. On first V2 activation, each present raw value is also copied into the versioned import namespace. |
| WebView localStorage | `<app>:v2:legacy-import:v1:<encoded-old-key>` | Schema 1 envelope containing the old key and raw old value | New preservation/staging copy for the future owning official plugin. It is not treated as an already-completed semantic plugin migration. |
| WebView localStorage | `<app>:v2:migration:v1` | Schema 1 completion marker and imported-key allowlist | Written only after all copies succeed. Missing marker is retryable; malformed marker fails safe to legacy and is not overwritten. |
| WebView localStorage | `<app>:runtime-mode` | Browser-preview-only schema 1 runtime mirror | Retained separately from the desktop app-config authority. Invalid data fails safe to legacy. |
| WebView localStorage | `<app>:v2:desktop-layout:v1` | Schema 1 `secondaryVisible` and `activePane` only | New optional V2 preference. It never contains paths, document text or session state. |
| WebView localStorage | `<app>:v2:plugin-storage:v1:<workspace-hash>:<plugin-id>:<key>` | Versioned JSON owned by one bundled plugin and one workspace | New bounded V2 namespace. The workspace identity is SHA-256-derived; values are limited to 64 KiB and a namespace to 1 MiB. |
| WebView localStorage | `<app>:storage-schema-version`; unprefixed `server`, `lastServerOk`, `apiUrl` | Existing legacy bootstrap migration | Unchanged. Only the legacy root executes its existing cleanup; the V2 migration does not expand that deletion set. |
| WebView IndexedDB | `files` / `handles` / `savedDirectoryHandle` | v0.0.5 browser File System Access handle | Retained and untouched. V2 desktop does not claim or delete this browser-only handle, so a legacy/browser rollback can still use it. |
| Cache Storage | Versioned service-worker resource cache | Generated application resources, not workspace data | Outside the data migration. Existing legacy cache lifecycle remains responsible for replacement/removal. |
| sessionStorage | `<app>:workspace-hint-dismissed` | Per-tab legacy UI hint | Ephemeral and intentionally not migrated. |

`<app>` is injected from `app.manifest.json`; it is not a second hard-coded product identity in the
migration implementation.

## Ordered migration

1. During Tauri setup, the host validates the app-config sources and app-data root without
   following symbolic links or reading oversized/non-regular inputs.
2. If a valid app-data completion ledger already exists, startup is idempotent. An invalid ledger
   is retained and causes V2 to fail closed.
3. Otherwise the host writes the expected ledger through the private sibling-temp, flush, atomic
   replace and directory-sync path. The existing app-config files are never rewritten.
4. Only after runtime resolution selects V2 does the frontend inspect localStorage. It copies the
   allowlisted values to the import namespace and writes the local completion marker last.
5. A read, write, quota or marker-validation failure changes the current runtime resolution to
   `legacy`. Partial import copies are harmless and can be overwritten on a later retry because the
   v0.0.5 source values remain authoritative.

## Rollback and compatibility

- v0.0.5 continues to see its original localStorage keys, IndexedDB handle and workspace bytes.
  It ignores all namespaced V2 records.
- Switching `runtime-mode.json` back to `legacy` requires a restart and does not delete V2 recovery
  or plugin state.
- Reinstalling the old binary does not require a reverse migration. Its unknown app-data files and
  localStorage namespaces are inert.
- Deleting or rewriting a corrupt marker automatically is forbidden. Diagnosis or a future
  separately versioned repair must be explicit so a failed migration cannot masquerade as success.
- The staged preference copies do not prove Phase 5 plugin adoption. Each official plugin must
  validate and migrate its own schema while continuing to preserve the old source key until its
  product acceptance gate closes.

Automated fixtures cover idempotence, byte-for-byte source retention, partial localStorage retry,
invalid schema/marker behavior, storage denial and legacy selection. Target-platform in-place
upgrade and reinstall/rollback remain manual release acceptance gates.
